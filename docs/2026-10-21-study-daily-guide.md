## 0. 모든 날에 공통인 틀

### 0-1. 하루 2시간 표준 시간표

| 구간 | 분 | 할 일 |
|------|----|-------|
| 시작 의식 | 5 | `git status --short --branch` → `nvm use 22.21.1` → 어제 기록의 "내일 할 일" 한 줄 확인 |
| 읽기 | 25 | 오늘 흐름의 코드와 학습 가이드 절. 복습 체크리스트 해당 항목을 먼저 소리 내어 답하고, 막힌 것만 본문으로 간다 |
| 가설 | 10 | 아래 0-2 참고. 미션 문서 §1을 열기 **전에** 적는다 |
| 재현 | 15 | 시뮬레이터에서 증상을 눈으로 본다. 재현 절차와 결과를 한 줄로 메모한다 |
| 수정 | 40 | 직접 타이핑. 막히면 0-3의 규칙을 따른다 |
| 검증 | 10 | `npm run typecheck` · `npm test` · `npx eslint .` · 같은 재현 절차 재실행 |
| 기록·설명 | 15 | `reviews/N-N.md` 작성 → 두 문장 설명 → 내일 할 일 한 줄 |

시간이 모자라면 줄이는 순서는 "수정 → 기록"이 아니라 **"읽기 → 재현"**이다. 기록과 설명을 빼면 완료로 치지 않는다 (start-guide §4 7단계).

### 0-2. "가설 먼저" 규칙

P1 퀴즈에서 나온 약점은 "무엇은 맞히는데 왜를 못 댐"과 "그럴듯한 오답에 낚임"이었다. 이 둘을 같이 잡는 방법이다.

1. 미션 문서에서 **README 목록의 한 줄 증상**과 위치(파일)만 본다. 미션 문서의 §1 "증상과 위치"에는 원인 추적이 이미 들어 있으니 아직 열지 않는다.
2. 해당 코드를 직접 읽고 원인 후보를 **2~3개** 적는다.
3. 후보에 **확률 순서**를 매기고, 각각 "이게 맞다면 화면에서 이런 증상이 나야 한다"를 한 줄씩 붙인다.
4. 그 다음에 §1을 읽어 대조한다. 내 후보 중 무엇이 맞았고 무엇이 틀렸는지가 `reviews/N-N.md`의 "문제점" 칸 재료가 된다.

가설이 전부 틀려도 괜찮다. 틀린 후보를 적어 두는 것이 목적이다.

### 0-3. 막힘 규칙

| 경과 | 행동 |
|------|------|
| 25분 막힘 | `N-N 힌트 1` 요청 (방향) |
| 다시 20분 | `힌트 2` (API 이름) |
| 다시 20분 | `힌트 3` (함정) |
| 힌트 3까지 갔는데도 30분 막힘 | 그날은 멈춘다. 막힌 지점을 기록에 쓰고 다음 버퍼 날에 이어간다 |

"정답 보여줘"는 하지 않는다. `직접 수정해줘`는 힌트 3까지 쓴 뒤에도 막혔을 때의 마지막 수단이고, 그렇게 했다면 기록에 적는다.

### 0-4. 끝내는 의식 (매일)

1. 검증 4종을 돌린다.
2. `git diff`를 훑어 **임시 코드**(임시 `console.log`, 일부러 넣은 실패, 바꿔 둔 URL)가 남지 않았는지 본다. 미션마다 임시 코드가 있는 곳은 아래에 따로 적었다.
3. 미션 범위 밖 파일이 diff에 없는지 본다.
4. 커밋은 미션당 두 개로 나눈다. 코드는 `fix:` / `refactor:` / `style:`, 기록은 `docs:`. 제목은 한국어 50자 이내, 본문은 WHY 중심. `--no-verify`는 쓰지 않는다. 커밋은 직접 하거나 요청한다.
5. `reviews/N-N.md`에 "내 코드 → 문제점 → 정답 → 암기 고리 → 가이드 근거"를 쓴다. ⚠️ 미션은 상단에 `⚠️ 동작 변경`과 변경 전후를 적는다.
6. 두 문장 설명을 소리 내어 말한다. 못 하면 내일 아침 첫 15분에 다시 한다.
7. 내일 할 일을 기록 맨 아래에 한 줄 적는다.

### 0-5. 밀렸을 때

- 버퍼 날(Day 7, 14, 21 등)이 첫 번째 흡수처다.
- 버퍼를 다 쓰고도 밀리면 **선행 관계가 없는 미션**부터 건너뛴다. 선행 관계가 있는 것(2-2→2-3, 2-4→2-5, 2-3·2-5→2-11, 3-1·2-8→3-2→3-3)은 순서를 지킨다.
- 하루가 밀려도 일정 전체를 바꾸지 않는다. 마지막 주의 P8 시작일이 늦어질 뿐이다.

### 0-6. 한 번만 확인할 것

- `README.md`가 staged(`A`) 상태다. 미션 3-3 문서는 이 파일을 "untracked"라고 적었으니 **문서와 현재 상태가 어긋나 있다.** 3-3 때 다시 확인한다. 그 전까지는 미션 커밋에 섞이지 않게 `git add`를 파일 단위로 한다.
- 가이드 문서(`docs/2026-10-21-*.md` 두 개)는 아직 untracked다.

|-----------|-------------|--------------------------|---------------------------|

빈 칸을 다 채운 뒤에 미션 §1의 경로 A~D를 읽고 대조한다.

**재현 — 두 갈래**
1. 경로 D (시뮬레이터): 로그인 → Metro에서 `r` 리로드 → 홈 → 네트워킹 → "보호된 API 호출 (1회)" → 로그에 "실패: 로그인 필요"가 나오는가. 화면은 로그인 상태인데 보호 API가 안 되는 불일치를 눈으로 본다.
2. 경로 B·C (코드): 화면으로는 도달하기 어렵다. **실패하는 테스트를 먼저 쓴다.** `login()`을 await하지 않고 `logout()`을 부른 뒤 `isLoggedIn()`을 확인하는 식이다. 빨갛게 되는 것을 확인한 다음에 고친다. (test-first가 이 미션의 정석이다.)

**코딩 전에 한 줄씩 정할 것**
- `refreshCount`: 로그아웃 때 리셋하나, 테스트가 호출 전후 차이로 비교하게 하나? 이유 한 줄.
- 진행 중 `login`/갱신이 로그아웃을 되살리지 못하게 하는 방식. 힌트 2에 "세대 값" 방식이 언급돼 있으니, 쓰기 전에 다른 방식과 장단을 한 줄씩 비교한다.
- 재시작 후 `user`는 있는데 `session`이 없는 불일치. 문서의 선택지 3개 중 하나를 고르고 **사용자 체감 동작이 어떻게 바뀌는지** 한 줄로 적는다. 보안(토큰을 디스크에 두는 것)과 UX를 같이 본다.

**수정 중 확인**
- 테스트를 같은 파일에 추가하면 모듈 상태를 공유한다. 테스트 순서를 바꿔도 통과하는지 확인한다.

## Day 3 · 10/24 (토) — 1-1 WebSocket 언마운트 후 재연결 누수

**목표**: `close()` 호출과 close 이벤트가 다른 시점이라는 것, 그래서 cleanup이 끝난 뒤에 새 타이머가 생기는 경로를 말로 설명한다.

**시간표**: 읽기 30 · 가설 10 · 재현 20 · 수정 35 · 검증 10 · 기록 15

**읽기**
- `src/api/network.ts`의 `connectEchoSocket`과 `src/screens/NetworkScreen.tsx` 전체(특히 `wsRef`·`manualCloseRef`·`timeoutRef`, 언마운트 cleanup, `openSocket`, `onClose`).
- `p6-study-guide.md` W16 절의 WebSocket 수명주기.

**가설**: "화면을 나간 뒤에 무엇이 남아서 돌까?"를 후보 2~3개로 적는다. 후보마다 "맞다면 Metro 로그에 이렇게 찍힌다"를 붙인다. 화면 로그는 언마운트 후에는 안 보이므로 **로그로 확인하는 설계**가 필요하다는 점이 이 미션의 포인트다.

**재현 (임시 코드 있음)**
1. `connectEchoSocket`의 `onopen`/`onclose`에 임시 `console.log`를 넣는다.
2. 연결 → 뒤로 가기 → Metro 터미널에서 close 로그 이후 500ms 이상 뒤에 open이 다시 찍히는지 본다.
3. 추가 경로도 한 번 시도한다: 재연결 대기 중에 "연결" 버튼을 눌러 소켓이 둘이 되는가.

**코딩 전에 한 줄씩 정할 것**
- 이미 있는 `manualCloseRef`를 재사용할지, 별도 "언마운트됨" 플래그를 둘지. 각각 StrictMode와 재마운트에서 어떻게 될지(힌트 3에 설명)를 비교하고 고른다.
- 플래그를 세우는 시점과 `close()` 호출의 **순서**. 순서가 바뀌면 무슨 일이 생기는지 설명할 수 있어야 한다.
- `openSocket` 첫 줄이 플래그를 `false`로 되돌리는 점이 내 설계와 충돌하지 않는지.
- 언마운트 후 `setWsConnected`/`appendLog`까지 막을지.

**검증**: 재현을 반복해 open 로그가 다시 찍히지 않는지. 그리고 **회귀**를 본다: 화면 안에서 "연결 끊기"와 서버발 끊김의 자동 재연결(최대 3회)이 기존처럼 동작하는지. `npm test`에는 이 화면 테스트가 없으므로 시뮬레이터가 유일한 검증이다.
**완료 기준**: 미션 §6 체크 + **임시 로그를 모두 지웠다** (`git diff`로 `network.ts`가 깨끗한지).
**기록 포인트**: 처음 가설이 무엇이었고 어디가 틀렸는지, 선택한 플래그 방식과 버린 방식.
**말로 설명**: `close()` 호출 시점과 `onClose` 호출 시점이 왜 다른가.

## Day 8 · 10/29 (목) — 2-4 HttpError 도입

**목표**: 에러에 상태 코드를 담는 전용 클래스를 만들고, 캐스트를 `instanceof`로 바꾼다.

**시간표**: 읽기 25 · 인벤토리 15 · 수정 45 · 검증 15 · 기록 20

**읽기**: `posts.ts`의 두 `throw`, `auth.ts`의 `status` 읽기/쓰기, `NetworkScreen`의 `catch`들. 이미 `instanceof`를 쓰는 곳(`FeedDetailScreen`, `NotificationScreen`, `LoginScreen`)과 비교한다.

**인벤토리 먼저 (grep으로)**
```bash
grep -rn "as Error\|Error & {" src
grep -rn "\.status" src
```
status를 쓰는 곳, 읽는 곳, 캐스트가 필요한 곳을 표로 만든다. 미션 문서의 표와 다르면 그 사실을 기록한다.

**실험 두 개 (코딩 전)**
- 캐스트 일부를 지워 보고 `tsc`가 실제로 에러를 내는지 본다. React Query v5의 기본 에러 타입이 `Error`라서 지워도 되는 캐스트가 있을 수 있다.
- 클래스를 만든 뒤 Hermes에서 `instanceof`가 실제로 `true`인지 임시 로그로 확인한다 (문서도 "확인 필요"로 남겼다). 확인 후 로그는 지운다.

**주의 두 가지**
- 던지는 곳을 **전부** 바꿔야 의미가 생긴다. 일부만 바꾸면 클래스가 있는데 쓰이지 않는다.
- `auth.ts`의 "로그인 필요"처럼 상태 코드가 없는 실패까지 `HttpError`로 만들지 않는다.
- 2-11에서 이 클래스를 Node로 테스트한다. `constructor(public status: number)` 같은 parameter property는 Node의 TS 실행에서 로드 단계에 실패한다. 필드를 명시적으로 선언한다. 지금 바꿔 두면 2-11에서 안 헤맨다.

**검증**: typecheck · eslint · `npm test` · Network 화면에서 "보호된 API 호출"을 4초 이상 기다린 뒤 눌러 401 → 갱신 → 재시도 흐름이 그대로인지.
**완료 기준**: `grep`에 남는 캐스트가 모두 "필요해서 남긴 것"이고 이유가 있다.
**말로 설명**: `catch (e)`의 `e`가 `unknown`인 이유와 `as` 캐스트의 위험.

## Day 12 · 11/2 (월) — 2-5 withRetryBackoff 개선

**목표**: "재시도해도 소용없는 에러"를 구분하고, 원본 에러를 `cause`로 보존하고, 취소 신호를 대기와 요청 양쪽에 연결한다.

**시간표**: 읽기 25 · 가설 10 · 설계 15 · 수정 45 · 검증 15 · 기록 10

**읽기**: `network.ts`의 `withRetryBackoff`, `NetworkScreen`의 재시도 데모(`flakyFetch`)와 호출부의 `message` 사용, `LocationScreen`의 `Promise.race`. MDN의 `Error.cause`, `AbortController`. `p6-study-guide.md` W16의 백오프·jitter 절.

**결정할 것**
- "다시 시도해도 소용없는 에러"를 알아보는 방법. 2-4의 결과물을 쓴다. `flakyFetch`는 `status` 없는 일반 `Error`를 던진다. "재시도하지 않을 에러"의 기본값을 정할 때 이 데모가 깨지지 않는지 먼저 확인한다.
- 호출부(`NetworkScreen`)가 원본 메시지를 읽는다. `message` 형식을 바꾸면 화면 로그가 달라진다. 바꿀지 유지할지 정한다.
- `signal`을 `fn`에 넘기는가, 대기에만 쓰는가. 대기만 쓰면 반쪽이다.
- abort 때 Promise는 reject했는데 타이머가 남는 경우를 어떻게 막는가. 이미 aborted인 signal을 받았을 때는?

**주의**
- `AbortSignal.timeout`, `AbortSignal.any`, `signal.throwIfAborted`가 Hermes(RN 0.81)에서 있는지는 확인 필요다. 기본 API만으로 시작한다.
- `LocationScreen`에서 고칠 것은 **타이머 정리뿐**이다. `getCurrentPositionAsync` 자체는 중단할 수 없다. 성공과 실패 어느 경로에서도 실행되는 블록이 무엇인지 생각한다.

**검증**: typecheck · eslint · `npm test` · Network 화면 재시도 데모에서 로그의 백오프 시간이 지수로 증가 · Location 화면 위치 가져오기가 기존처럼 동작.

## Day 15 · 11/5 (목) — 2-8 접근성

**목표**: 의미 없는 컨테이너(`Pressable`, `View`)에 role·label·state를 직접 알려야 한다는 것을 이해하고, 공통 컴포넌트 `Btn`부터 고친다.

**시간표**: 읽기 20 · 현황 점검 25 · 수정 45 · 검증 20 · 기록 10

**읽기**: `Btn.tsx`(33줄), RN 0.81 Accessibility 문서(`role` / `accessibilityRole` 우선순위), `Pressable` 문서의 `hitSlop`. `p2-study-guide.md` §8 + `p1-study-guide.md` §3-1(스타일 배열).

**현황 점검**
```bash
grep -rn "accessib\|aria-\|role=\|hitSlop" src
```
`Btn`, `TextInput` 5곳, 직접 쓴 `Pressable`(`ComposeScreen`, `FeedListScreen` 시트 옵션, `FeedSectionsScreen`)을 표로 만들고, 각각 "이게 지금 스크린 리더에 어떻게 읽히나"를 적는다. Xcode의 **Accessibility Inspector**로 시뮬레이터 요소의 role·label·state를 직접 본다. 처음이면 이 절차 자체가 오늘의 학습이다.

**확인할 것 (힌트 3)**
- `role`이 `accessibilityRole`보다 우선한다. 둘을 섞지 않는다.
- `Pressable`이 `disabled`를 `accessibilityState`에 자동으로 합쳐 주는지 RN 소스(`node_modules/react-native/Libraries/Components/Pressable/Pressable.js`)에서 직접 본다. 이미 있는 것을 중복으로 넣지 않는다.
- `Btn`은 텍스트 자식이 있어 자동 라벨이 있다. 라벨을 덮어쓰면 화면 글자와 달라질 수 있다.
- `hitSlop`: `Btn`은 높이가 이미 충분할 수 있다. 필요한 대상을 먼저 정한다. 이웃 버튼 쪽으로 넓히면 오터치가 난다.

**연결**: 3-2에서 `ComposeScreen`의 수제 `Pressable`이 `Btn`으로 바뀐다. 그때 `Btn`이 같은 `hitSlop` 효과를 내야 한다. 오늘 `hitSlop`을 둘 곳과 이유를 기록에 남긴다.

**검증**: Accessibility Inspector에서 `Btn`의 role=button, 비활성/진행 중 상태, 로그인 입력란의 label. 화면 모양과 레이아웃이 그대로.
**말로 설명**: 웹 `<button>`과 RN `Pressable`이 접근성 정보에서 다른 점. `placeholder`가 `label`을 대신할 수 없는 이유.

## Day 21 · 11/11 (수) — 3-1 색상 hex와 URL 상수화

**목표**: RN에는 CSS 변수가 없으므로 JS 모듈 상수가 그 역할을 한다는 것을 이해하고, 화면 모양을 바꾸지 않고 색과 URL을 한 곳으로 모은다.

**시간표**: 읽기 15 · 기준선 25 · 설계 15 · 수정 40 · 검증 20 · 기록 15

**읽기**: `theme/styles.ts`의 `colors`(`ghostText` 하나뿐인 이유와 이름 체계), `Btn.tsx`. 이 미션에서 새 API는 없다. `RefreshControl`, `ActivityIndicator`, `placeholderTextColor`처럼 **style 바깥 props**에 색이 들어가는 곳이 놓치기 쉽다.

**기준선 (코딩 전)**
```bash
grep -rn "#8a92a6\|#93c5fd" src App.tsx            # 줄 수를 기록
grep -rnE "https?://|wss?://" src App.tsx          # URL 위치
```
문서의 숫자(10, 9, URL 5곳)와 현재 숫자를 비교해 어긋나면 기록한다. 시뮬레이터에서 **탭바 활성/비활성 색, 스피너 색, placeholder 색, pull-to-refresh 색을 미리 스크린샷**으로 남겨 둔다. 이 미션은 화면이 달라지면 안 된다.

**사용처 표**: 각 색의 사용처를 "style 안 / props 안"으로 나눠 표로 만든다.

**결정할 것**
- 토큰 이름 규칙: 기존 `ghostText`는 "쓰임새" 이름이다. 지금 같은 값이 스피너·탭 활성색에도 필요하다. 쓰임새 기준을 이어갈지 의미 기준으로 바꿀지 한 줄 규칙으로 정한다.
- URL: 환경별로 바뀌는 값인가, 단순히 한곳에 모으면 되는 값인가. `FeedListScreen`의 썸네일은 id가 들어가는 템플릿이다.
- 값이 같아도 의미가 다른 색(`#2b3446` 등)은 합치지 않는다. 필수 범위는 위 두 색이다.

**주의**
- 토큰 정의가 `StyleSheet.create` 위에 있어야 참조할 수 있다.
- 토큰을 별도 파일로 빼면 순환 import가 생길 수 있다 (`Btn.tsx`가 이미 `styles.ts`에 의존).
- 정규식 일괄 치환은 `#fff`나 주석까지 건드린다. 한 곳씩 바꾸고 `tsc`를 자주 돌린다.

**검증**: typecheck · `npm test` · eslint · 위 grep 두 개(토큰 정의 외에 남은 곳 없음) · 기준선 스크린샷과 비교 · 업로드와 WebSocket이 계속 동작.
**말로 설명**: RN에서 색이 `StyleSheet` 밖(props)에 들어가는 사례와 이유.

**③ 재측정**: 어제와 **같은 시나리오 4개**로 "후" 표를 만든다. 수정한 항목마다 "어떤 수치가 이 수정을 정당화했는가"를 한 줄로 쓴다. 삭제 스와이프, 롱프레스 시트, 무한스크롤이 변경 전과 같은지 확인한다.

**④ README 문구 갱신 (사용자 직접 과제)**
루트 `README.md`의 "한계" 절에 "성능 최적화(`React.memo`, `getItemLayout`)와 접근성은 다루지 않음."이라는 문장이 있다. 이제 사실과 다르다. **Claude는 이 문장을 써 주지 않는다. 직접 고친다.**
- 무엇을 다뤘고 무엇을 **여전히 안 다뤘는지** 구분해서 쓴다. `getItemLayout`을 적용하지 않았다면 그대로 남긴다.
- 측정 결과 `memo`를 적용하지 않았다면 "측정 후 불필요 판단"이라고 쓰는 것이 정확하다.
- 이 파일의 git 상태를 먼저 확인한다 (지금은 staged인데 미션 문서는 untracked라고 적었다). 커밋 대상인지 확인 후 진행한다.

**말로 설명**: `memo`가 막아 주는 것과 막지 못하는 것(인라인 콜백, `children`). dev 모드 측정값을 어떻게 읽어야 하는가.
