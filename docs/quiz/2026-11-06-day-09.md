## 문항별 상세

### 1. `push` 후 `setEntries(entries)`가 화면을 갱신하지 않는 이유 — 부분 정답

**내 답**
> push 메소드를 쓰면 리액트가 렌더링 대상으로 간주하지 않고 건너뜀. 올바른 코드는 `setEntries([...newEntry])`
> (이후 덧붙임) 올바른 답은 `setEntries([newEntry, ...entries])`

**문제점**
- 결과("건너뜀")는 맞지만 이유가 빠졌다. 건너뛰는 근거는 `push`라는 메서드 자체가 아니라 "setter에 넘긴 값이 이전과 같은 참조"라는 점이다. 같은 배열을 수정한 뒤 같은 참조를 넘기면 React는 변경이 없다고 본다.
- 처음 쓴 코드 `[...newEntry]`는 `newEntry`를 펼친 것이라 기존 `entries`가 사라진다. 객체라면 배열 spread 자체가 오류다. 직접 고쳐 적은 것은 좋다.

**정답**
```ts
// 틀림: 같은 배열 참조
entries.push(newEntry);
setEntries(entries);

// 맞음: 새 배열
setEntries([newEntry, ...entries]);
```

**암기 고리**: React는 내용이 아니라 참조를 본다. state는 고치지 말고 새로 만들어 넘긴다.

**근거**: Day 5 카드의 "검증(10분)", "이해 점검 질문" 절.

### 2. `value` 없는 `TextInput`에서 `setTitle('')`이 입력창을 못 비우는 이유 — 부분 정답

**내 답**
> value 자체가 없기 때문에 Input에 값을 입력해도 값이 감지가 안되기 때문

**문제점**
- 방향이 거꾸로다. 입력값은 `onChangeText`로 state에 잘 감지된다. 문제는 반대 방향, 즉 state가 입력창으로 흘러가지 않는 것이다.
- "비제어 입력"이라는 핵심 개념어가 없다.

**정답**
```tsx
// 비제어: 글자는 네이티브 입력창이 쥔다. setTitle('')이 입력창에 닿지 않는다.
<TextInput onChangeText={setTitle} />

// 제어: state가 입력창의 값을 결정한다.
<TextInput value={title} onChangeText={setTitle} />
```

**암기 고리**: `onChangeText`는 입력창 → state, `value`는 state → 입력창. 양방향을 다 이어야 제어 입력이다.

**근거**: Day 5 카드의 "예측(10분)", "검증(10분)" 절.

### 3. 키보드 상태에서 `ScrollView` 안 저장 버튼 첫 탭 무반응 — 모름

**내 답**
> 제대로 모르겠음

**문제점**: 전체 미응답. 원인(키보드 닫기 탭이 자식에게 전달되지 않음)과 해결(`keyboardShouldPersistTaps`), `behavior` 플랫폼 지정 세 가지를 모두 놓쳤다.

**정답**
```tsx
<KeyboardAvoidingView
  behavior={Platform.OS === 'ios' ? 'padding' : 'height'}
  style={{ flex: 1 }}
>
  <ScrollView keyboardShouldPersistTaps="handled">
    {/* 저장 버튼 */}
  </ScrollView>
</KeyboardAvoidingView>
```
`keyboardShouldPersistTaps` 기본값 `never`에서는 키보드가 열려 있을 때 첫 탭이 키보드를 닫는 데만 쓰이고 자식 버튼은 받지 못한다. `handled`면 자식이 처리한 탭은 그대로 전달된다.

**암기 고리**: 첫 탭은 키보드가 먹는다. 막으려면 `handled`.

**근거**: Day 6 카드의 "예측(10분)", "검증(10분)" 절.

### 4. `FlatList`의 기본 key와 key가 중요한 상황 — 대체로 정답

**내 답**
> index로 정해짐. key가 중요한 상황은 아이템 정렬이 필요할 때 가장 중요하게 작용하낟.

**문제점**
- "index"는 맞지만 순서(`item.key` → `item.id` → index)가 빠졌다. 데이터에 `id`가 있으면 `keyExtractor` 없이도 `id`가 쓰인다.
- 상황이 "정렬"으로 좁다. 삽입·삭제·재정렬 전부가 해당한다. 이 앱의 피드는 새 글을 맨 앞에 넣으므로 삽입이 가장 직접적인 사례다.
- 왜 중요한지(상태가 엉키거나 불필요한 재렌더)가 없다.

**정답**
```tsx
<FlatList
  data={entries}
  keyExtractor={(item) => item.id}
  renderItem={...}
/>
```
index key에서는 맨 앞에 항목을 넣으면 모든 항목의 key가 한 칸씩 밀려, 항목에 딸린 상태가 엉뚱한 항목에 붙고 전체가 다시 렌더된다.

**암기 고리**: key는 위치가 아니라 신원이다. 순서가 바뀔 수 있으면 index를 쓰지 않는다.

**근거**: Day 7 카드의 "검증(10분)", Day 8 카드의 "리스트 성능 기본" 관련 절.

### 5. `RefreshControl`의 `refreshing`이 `false` 고정 — 모름

**내 답**
> 잘 모르겠음

**문제점**: 전체 미응답. `refreshing`이 제어 prop이라는 점이 핵심인데, 2번(제어 입력)과 같은 구조다.

**정답**
```tsx
const [refreshing, setRefreshing] = useState(false);

const onRefresh = async () => {
  setRefreshing(true);
  await reload();
  setRefreshing(false);
};

<FlatList refreshControl={<RefreshControl refreshing={refreshing} onRefresh={onRefresh} />} />
```
`onRefresh`는 당겼다는 알림만 준다. `refreshing`을 `true`로 올리는 것은 부모 몫이다. 안 올리면 값이 계속 `false`라 인디케이터가 바로 사라진다.

**암기 고리**: `refreshing`도 `value`와 같다. 부모가 쥐고 있는 값이다.

**근거**: Day 8 카드의 "예측(10분)", "검증(10분)" 절.

## 종합 약점 패턴

1. **제어(controlled) prop 구조를 못 잇는다.** 2번(`value`)과 5번(`refreshing`)은 같은 원리다. 자식 컴포넌트가 값을 알려주는 것과 부모가 값을 내려주는 것은 별개의 방향이고, 둘을 모두 이어야 동작한다. 한 번 원리로 정리해 두면 두 문항이 함께 해결된다.
2. **결과는 맞히는데 이유를 못 댄다.** 1번은 "건너뜀"까지만, 4번은 "index"까지만 썼다. 퀴즈 안내문의 "맞은 뒤에도 왜를 한 문장으로"를 아직 습관으로 못 만들었다. 이유 자리에 "참조", "신원" 같은 개념어를 넣는 연습이 필요하다.
3. **키보드·리프레시처럼 네이티브 동작이 얽힌 항목에서 약하다.** 3번은 전체가 빈칸이다. 웹에는 없는 개념("첫 탭은 키보드가 먹는다")이라 Day 6 카드의 "웹과 다른 점" 절을 함께 보면 좋다.
4. **상황을 좁게 일반화한다.** 4번의 "정렬"은 맞지만 삽입·삭제를 빠뜨렸다. 이 앱에서 실제로 일어나는 동작(새 글 맨 앞 삽입)에 대입해 보는 습관이 필요하다.
