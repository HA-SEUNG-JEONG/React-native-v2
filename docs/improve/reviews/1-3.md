## 문항별 상세

### 1. `isReady`가 없으면 부팅 때 무슨 화면이 보이나 — 부분정답

- **내 답**:
  > 부팅 때 잠깐 로그인 화면이 보일 수 있음
  > 만약 이미 로그인이 되어 있는 경우라면 프로필 페이지에서는 로그아웃 버튼 및 탭 네비게이터에는 홈/프로필 탭이 보임
  >
  > (정정 1) isReady의 역할은 AUTH_KEY에서 가져온 값을 SecureStore에 저장하는 역할을 담당한다. 이 값을 제대로 받아오지 못하는 경우도 발생할 수 있는데, 이 경우에는 인증 상태가 제대로 적용되어 있는지 알 방법이 없다. 그래서 isReady로 분기 처리를 하는 것이다.
  >
  > (정정 2) isReady는 SecureStore 읽기가 끝났음을 알리는 플래그. 없으면 user === null 상태로 첫 렌더가 나가서, 로그인한 사용자에게도 로그인 화면이 잠깐 보인다. isReady는 저장하는게 아니라 boolean state. isReady는 인증을 판정하는 용도로 쓰이는 게 아님
- **문제점**:
  - 첫 답의 둘째 문장이 첫 문장과 모순된다. 이미 로그인된 사용자도 첫 렌더에서는 `user === null`이라 로그인 화면이 보인다. 프로필/탭이 보이는 건 읽기가 끝나 `user`가 채워진 뒤의 모습이다.
  - 정정 1에서 `isReady`를 "SecureStore에 저장하는 역할"로 적었는데, 저장이 아니라 읽기 완료 신호다. 정정 2에서 이미 고쳤다.
  - 정정 1의 "받아오지 못하는 경우 알 방법이 없다"도 부정확하다. 실패해도 `.catch`가 `setUser(null)`로 "로그아웃 상태"로 취급하고 `.finally`가 `setIsReady(true)`를 보장한다. 그래서 앱이 멈추지 않는다.
- **정답**: `isReady`는 "SecureStore 조회가 끝났다"는 boolean state다. 없으면 첫 렌더가 `user === null`로 나가 `RootNavigator`가 `AuthStack`(로그인 화면)을 먼저 마운트하고, 조회가 끝나면 `RootStack`으로 교체된다. 로그인한 사용자 눈에는 로그인 화면이 깜빡였다 사라진다.
  ```tsx
  // App.tsx
  const [isReady, setIsReady] = useState(false);
  useEffect(() => {
    SecureStore.getItemAsync(AUTH_KEY)
      .then(setUser)
      .catch(() => setUser(null))      // 실패 = 로그아웃 상태로 취급
      .finally(() => setIsReady(true)); // 성공/실패 무관하게 게이트 해제
  }, []);
  if (!isReady) return <View style={[styles.screen, styles.center]} />; // 렌더 자체를 미룸
  ```
- **암기 고리**: `isReady` = "읽기 끝났나?" 플래그. 저장도 판정도 아님. 끝나기 전엔 빈 화면, 끝나면 `user` 값대로 분기.
- 근거: `docs/p5-study-guide.md` W13 절의 "부팅 시 조회 — 로딩 게이트가 없으면 화면이 깜빡인다". 코드는 `App.tsx`의 `isReady` state와 `useEffect`.

### 2. 왜 `if (!user) redirect`가 아니라 네비게이터 교체인가 — 부분정답

- **내 답**:
  > 로그인 직후 뒤로 가기를 누른다면 로그인이 됐는지 명확하게 알 수 없음
  > 로그아웃을 하더라도 /home이 스택에 남아있다면 로그인/로그아웃을 반복적으로 실행했을 때 스택 관리가 어떻게 이루어지는지 헷갈릴 가능성이 있음
  >
  > (정정) 만일 redirect 방식을 쓴다면 스택 히스토리가 계속 쌓이게 된다. 이 과정에서 로그인 이후 뒤로 가기를 누른다면 redirect를 썼기 때문에 로그인 화면이 보이는 것이다. 보호 화면이 마운트 되고 redirect 되면 화면이 깜빡일 가능성이 있어 UX에 좋지 않다. 로그아웃 하면 RootStack.Navigator가 통째로 언마운트 되기 때문에 보호 화면으로 돌아갈 스택 자체가 없다.
- **문제점**:
  - 1차 답은 "헷갈릴 가능성"처럼 개발자의 혼란을 이유로 들었다. 이건 설계 근거가 되지 못한다. 근거는 사용자에게 실제로 보이는 동작(뒤로 가기, 깜빡임, 보호 화면 노출)이어야 한다.
  - 정정본은 세 가지(히스토리 누적 / 깜빡임 / 언마운트로 스택 소멸)를 정확히 짚었다.
  - 빠진 것: 이 패턴의 핵심 가치인 보안 효과. 로그아웃 후 뒤로 가기로 캐시된 보호 화면이 다시 보이는 문제가 구조적으로 불가능해진다는 점을 한 문장으로 못 박지 않았다.
- **정답**: redirect 방식은 보호 화면을 먼저 마운트한 뒤 이동시키므로 (1) 스택에 화면이 쌓이고 뒤로 가기로 되돌아올 수 있으며, (2) 마운트 → redirect 사이에 깜빡임이 생긴다. 네비게이터 교체는 `user` 값에 따라 렌더하는 네비게이터 자체가 달라진다.
  ```tsx
  // src/navigation/index.tsx — RootNavigator
  const { user } = useAuth();
  if (user == null) {
    return <AuthStack.Navigator>...</AuthStack.Navigator>; // 보호 화면은 트리에 아예 없음
  }
  return <RootStack.Navigator>...</RootStack.Navigator>;   // 로그아웃 시 통째로 언마운트
  ```
- **암기 고리**: redirect = "들어갔다가 쫓아냄"(스택에 흔적이 남음). 네비게이터 교체 = "문 자체가 없음"(갈 곳이 없으니 못 돌아감).
- 근거: `docs/p3-study-guide.md` §3 "인증 게이트 = 네비게이터 교체"의 "이 방식의 자동 보안 효과" 단락, 복습 체크리스트 마지막 항목. 코드는 `src/navigation/index.tsx`의 `RootNavigator`.

### 3. `login()`과 `signIn()`은 각각 무엇을 어디에 저장하나 — 부분정답

- **내 답**:
  > login -> auth.ts 자체 메모리에 저장되기 때문에 앱을 종료하면 login 과정에서 생성된 토큰은 사라짐
  > signIn -> SecureStore에 user 이름을 저장하기 때문에 앱을 종료해도 사라지지 않음, 재시작하면 user는 남지만 토큰은 사라지는 불일치가 발생한다.
  > 결국 login, signIn은 서로 다른 저장소에 토큰이 저장됨
- **문제점**:
  - 앞의 두 줄은 정확하다. 특히 "재시작하면 user는 남지만 토큰은 사라지는 불일치"는 이 문제의 핵심 결론이다.
  - 마지막 문장이 틀렸고 앞 두 줄과도 모순된다. `signIn`은 토큰을 저장하지 않는다. 토큰은 `auth.ts`의 메모리에만 있고, SecureStore에는 user 이름만 있다. "서로 다른 저장소에 토큰이 저장됨"이 아니라 "서로 다른 저장소에 서로 다른 값이 저장됨"이다.
  - 빠진 것: 둘의 호출 관계. `LoginScreen.tsx`는 `await login(...)`이 성공한 뒤에야 `signIn(username)`을 부른다. 둘은 독립된 상태이고, 이어 붙이는 코드는 화면에 있다.
- **정답**: 저장 값과 저장소를 짝지어 외운다.

  | 함수 | 저장 값 | 저장소 | 앱 재시작 후 |
  |------|---------|--------|--------------|
  | `login()` | 토큰(`accessToken`, `refreshToken`) | `src/api/auth.ts`의 모듈 변수 `session` (메모리) | 사라짐 |
  | `signIn()` | user 이름 | SecureStore의 `AUTH_KEY` | 남음 |

  ```tsx
  // LoginScreen.tsx
  await login(values.username, values.password); // 토큰 → 메모리
  signIn(values.username);                        // 이름 → SecureStore (낙관적: 저장 실패해도 이번 세션은 로그인)
  ```
  재시작하면 `user`는 복원되어 로그인 화면을 건너뛰지만 `session`은 `null`이라 `fetchProtected()`가 "로그인 필요"로 실패한다.
- **암기 고리**: 이름은 금고(SecureStore)에, 토큰은 주머니(메모리)에. 앱을 끄면 주머니만 비워진다.
- 근거: `docs/p5-study-guide.md` W13 절(로그인 영속화). 코드는 `src/api/auth.ts`의 `session` 변수와 `login()`, `App.tsx`의 `signIn`.
- **보강 예정**: `docs/study/day-03.md`의 Q3 보강 항목에서 "같은 저장소인가?"에 한 문장으로 직접 답하기.

### 4. `signOut`은 무엇을 하나 — 부분정답

- **내 답**: 모듈 상태를 리셋 -> 쿼리 상태를 비움 -> 유저 state를 리셋 -> 기기 저장소에 있던 것들을 다 지움
- **문제점**:
  - 네 단계 순서는 `App.tsx`의 `signOut`과 일치한다.
  - "기기 저장소에 있던 것들을 다 지움"은 뭉뚱그림이다. 실제로 SecureStore에서 지우는 건 `AUTH_KEY` 하나다. 쿼리 캐시(AsyncStorage)는 마지막 단계가 아니라 두 번째 단계 `queryClient.clear()`가 영속 캐시에도 빈 상태로 반영해서 비운다. 대기 중이던 좋아요 뮤테이션 큐도 이때 폐기된다.
  - 첫 단계 "모듈 상태를 리셋"은 이 브랜치에서 아직 동작하지 않는다. `src/api/auth.ts`의 `logout()` 본문이 미션 1-6 TODO 주석만 있는 빈 스텁이라 `session` 등 모듈 변수가 그대로 남는다.
- **정답**: 호출 순서대로 4단계, 각 단계가 지우는 대상과 저장소를 붙여 적는다.
  1. `logout()` — `auth.ts` 모듈 상태(`session` 등) 리셋 (**현재 스텁이라 미구현**)
  2. `queryClient.clear()` — 메모리 쿼리/뮤테이션 캐시 + 영속 캐시(AsyncStorage) + 대기 중 좋아요 큐
  3. `setUser(null)` — React state, 이 시점에 `RootNavigator`가 `AuthStack`으로 교체됨
  4. `SecureStore.deleteItemAsync(AUTH_KEY)` — 기기에 저장된 user 이름 (실패하면 `persistError` 배너)
- **암기 고리**: 네 곳을 지운다 — 메모리 변수, 쿼리 캐시(+그 영속본), React state, SecureStore 한 키. "기기 저장소 전부"가 아니라 "키 하나".
- 근거: `App.tsx`의 `auth` useMemo 안 `signOut`. 모듈 변수 목록은 `src/api/auth.ts` 상단의 `session` / `refreshInFlight` / `loginInFlight` / `refreshCount`.
- **보강 예정**: `docs/study/day-03.md`의 Q4 보강 항목에서 4단계를 코드 호출 순서대로 다시 쓰고, 빈 `logout()`을 채우는 것까지 연결.

## 종합 약점 패턴

1. **구조는 맞히는데 경계 한정어에서 흔들린다.** Q3의 "토큰이 서로 다른 저장소"(실제는 서로 다른 값), Q4의 "다 지움"(실제는 키 하나). 무엇이 어디에 있는지는 알지만 "무엇을, 몇 개를" 정확히 못 박지 않는다.
2. **1차 답이 사용자에게 보이는 동작이 아니라 막연한 느낌으로 시작한다.** Q1은 방향이 반대였고, Q2는 "헷갈릴 가능성"이었다. 정정본에서야 실제 동작(깜빡임, 언마운트)이 나온다. 먼저 "화면에 무엇이 보이나"부터 적는 습관이 필요하다.
3. **정정본이 한 번 더 정정될 만큼 확신 없이 쓴다.** Q1은 정정이 두 번 나왔다. 코드를 열어 확인한 뒤 쓰면 첫 정정에서 끝난다.
4. **"왜"의 핵심(보안)을 빠뜨린다.** Q2의 정정본은 현상 3가지는 맞췄지만 이 패턴이 존재하는 가장 큰 이유(로그아웃 후 보호 화면 접근 차단)를 말하지 않았다.
