# 학습 공통 규칙 (매일 적용)

각 Day 카드(`day-NN.md`)는 이 규칙 위에서 돈다. 카드에는 규칙을 다시 쓰지 않고 날짜별 할 일만 둔다. 미션 문서의 힌트온리 규칙을 그대로 따른다: 카드에는 정답 코드가 없다.

## 1. 하루 90분 표준 시간표

| 구간 | 분 | 할 일 |
| --- | --- | --- |
| 시작 의식 | 5 | `git status --short --branch` → `nvm use 22.21.1` → 어제 기록의 "내일 할 일" 한 줄 확인 |
| 읽기 | 15 | 오늘 흐름의 **코드만** 읽는다. `p*-study-guide`의 체크리스트와 절 읽기는 금요일 버퍼로 옮긴다 |
| 가설 | 10 | 아래 2번 참고. 미션 문서 §1을 열기 **전에** 적는다 |
| 재현 | 10 | 시뮬레이터에서 증상을 눈으로 본다. 재현 절차와 결과를 한 줄로 메모한다 |
| 수정 | 35 | 직접 타이핑. 막히면 3번의 규칙을 따른다 |
| 검증 | 5 | `npm run typecheck` · `npm test` · `npx eslint .` · 같은 재현 절차 재실행 |
| 기록·설명 | 10 | `reviews/N-N.md` 작성 → 두 문장 설명 → 내일 할 일 한 줄 |

- 시간이 모자라면 줄이는 순서는 "수정 → 기록"이 아니라 **"읽기 → 재현"**이다. 기록과 설명을 빼면 완료로 치지 않는다 ([start-guide](../2026-10-21-study-start-guide.md) §4 7단계).
- **90분을 넘기면 그날은 멈춘다.** 남은 일은 "내일 할 일" 한 줄로 적고 금요일 버퍼가 흡수한다. 다음 날 분량에 얹지 않는다.
- 이틀로 나눈 미션은 첫째 날에 "복원·분류표·재현"까지, 둘째 날에 "설계 결정·수정·기록"을 한다.

## 2. "가설 먼저" 규칙

1. 미션 문서에서 **README 목록의 한 줄 증상**과 위치(파일)만 본다. 미션 문서의 §1 "증상과 위치"에는 원인 추적이 이미 들어 있으니 아직 열지 않는다.
2. 해당 코드를 직접 읽고 원인 후보를 **2~3개** 적는다.
3. 후보에 **확률 순서**를 매기고, 각각 "이게 맞다면 화면에서 이런 증상이 나야 한다"를 한 줄씩 붙인다.
4. 그 다음에 §1을 읽어 대조한다. 내 후보 중 무엇이 맞았고 무엇이 틀렸는지가 `reviews/N-N.md`의 "문제점" 칸 재료가 된다. 가설이 전부 틀려도 괜찮다. 틀린 후보를 적어 두는 것이 목적이다.

## 3. 막힘 규칙

| 경과 | 행동 |
| --- | --- |
| 15분 막힘 | `N-N 힌트 1` 요청 (방향) |
| 다시 15분 | `힌트 2` (API 이름) |
| 다시 15분 | `힌트 3` (함정) |
| 힌트 3까지 갔는데도 20분 막힘 | 그날은 멈춘다. 막힌 지점을 기록에 쓰고 다음 버퍼 날에 이어간다 |

"정답 보여줘"는 하지 않는다. `직접 수정해줘`는 힌트 3까지 쓴 뒤에도 막혔을 때의 마지막 수단이고, 그렇게 했다면 기록에 적는다.

## 4. 끝내는 의식

1. 검증 4종(typecheck · test · eslint · 재현 재실행)을 돌린다.
2. `git diff`를 훑어 **임시 코드**(임시 `console.log`, 일부러 넣은 실패, 바꿔 둔 URL)가 남지 않았는지 본다. 미션마다 임시 코드가 있는 곳은 각 카드 `## 참고`에 있다.
3. 미션 범위 밖 파일이 diff에 없는지 본다.
4. 커밋은 미션당 두 개로 나눈다. 코드는 `fix:` / `refactor:` / `style:`, 기록은 `docs:`. 제목은 한국어 50자 이내, 본문은 WHY 중심. `--no-verify`는 쓰지 않는다. 커밋은 직접 하거나 요청한다.
5. `reviews/N-N.md`에 "내 코드 → 문제점 → 정답 → 암기 고리 → 가이드 근거"를 쓴다. ⚠️ 미션은 상단에 `⚠️ 동작 변경`과 변경 전후를 적는다.
6. 두 문장 설명을 소리 내어 말한다. 못 하면 내일 아침 첫 15분에 다시 한다.
7. 내일 할 일을 기록 맨 아래에 한 줄 적는다.

## 5. 밀렸을 때

상황별 표, 60분판, 자르기 순서, 이월 로그는 [2026-10-24-study-missed-day-plan.md](../2026-10-24-study-missed-day-plan.md)에 있다.

- 버퍼 날(매주 금요일: 10/30, 11/6, 11/13, 11/20, 11/27)이 첫 번째 흡수처다. 버퍼에는 밀린 미션, 각 Tier 종료 절, `p*-study-guide` 체크리스트 구술이 들어간다.
- 줄일 수 있는 항목은 이 순서로 자른다: 2-5의 `AbortSignal`, 3-3 ②의 `AuthContext` 분리, 3-4의 CI 워크플로.
- 버퍼를 다 쓰고도 밀리면 **선행 관계가 없는 미션**부터 건너뛴다. 선행 관계가 있는 것(2-2→2-3, 2-4→2-5, 2-3·2-5→2-11, 3-1·2-8→3-2→3-3)은 순서를 지킨다. 스텁 브랜치에서는 1-4→1-5(알림 훅 복원)와 1-2↔2-3(삭제 성공 후 행 제거)도 이어져 있다.
- 하루가 밀려도 일정 전체를 바꾸지 않는다. 마지막 주의 P8 시작일이 늦어질 뿐이다.

## 6. 스텁 브랜치(`improve/missions-empty`) 요약

- 기준선: `npm run typecheck` 통과 · `npm test` 1건 통과(약 5.8초) · `npx eslint .` 3 errors / 2 warnings (errors 3은 `Btn.tsx`·`ComposeScreen.tsx`·`LoginScreen.tsx`의 prettier, warnings 2는 `NotificationScreen`의 미사용 `permissionError`와 `ProfileScreen`의 미사용 `e`). 비운 곳은 `grep -rn "TODO(미션" src App.tsx`로 찾는다.
- 스텁은 "있는 코드를 고치는 미션"을 "없는 코드를 처음 쓰는 미션"으로 바꿨다. 그래서 재현할 증상이 아직 없고, 증상 대신 "무엇이 비어 있는지"를 먼저 확인한다.
- 작업은 두 단계다. 1단계는 원래 코드가 하던 기본 동작을 가장 단순하게 복원하는 것, 2단계가 미션 본론이다. 1단계의 단순판은 미션이 고치려는 버그를 그대로 품고 있을 수 있고, 그것을 직접 재현한 뒤 2단계에서 고치는 것이 의도된 흐름이다. `reviews/N-N.md`의 "변경 전"은 이 단순판의 동작이다.
- 서로의 복원을 전제로 하는 쌍: 1-4→1-5(알림 훅), 1-2↔2-3(삭제 성공 후 행 제거). 일부 확인이 다른 날로 밀린다.
- 원본(`improve/missions`)은 열지 않는다. 1단계가 막히면 3번의 힌트 규칙으로 요청한다. 1단계는 "버그 없는 정답"을 목표로 하지 않는다. 미션별 시작 상태는 각 Day 카드의 "시작 상태"에 있다.
