> **오늘의 핵심**: 수치가 없으면 고치지 않는다 — 어제 측정이 정당화한 항목만 수정하고, "고치지 않음"으로 판단한 기록도 산출물이다.

**시작 상태**: [Day 31](./day-31.md)에서 쓴 `docs/improve/reviews/3-3.md`의 "전" 표가 출발점이다. 스텁이 건드리지 않은 미션이다. 표에 근거가 없는 후보는 오늘 건드리지 않는다.

## 끝 조건
1. 후보 5개 모두 "고친다/안 고친다"와 근거 수치가 적혀 있고(안 고친 후보 포함), "후" 표의 시나리오 4개가 "전" 표와 같은 순서·상태이며, 삭제 스와이프·롱프레스 시트·무한스크롤이 변경 전과 같다.
2. 검증 4종이 통과하고, 루트 `README.md`의 "한계" 문장을 내가 직접 고쳤다 (다룬 것과 여전히 안 다룬 것을 구분).
3. 말로 설명: `memo`가 막아 주는 것과 막지 못하는 것(인라인 콜백, `children`). dev 모드 측정값을 어떻게 읽어야 하는가.

## 막히면
- `memo`를 붙였는데 렌더 횟수가 안 줄면: 인라인 콜백이 그대로인지, 콜백을 안정화했는데도 `children`(JSX)이 새 요소인지 Profiler에서 어디서 깨지는지부터 본다. 15분 막히면 `3-3 힌트 3`(함정)을 요청한다 (정답 코드는 요청하지 않는다).
- `AuthContext` 분리가 `App.tsx`의 Provider 구조와 `useAuth` 소비자 3곳을 모두 건드려 꼬이면: 측정에서 이득이 없다면 되돌린다. 이것이 정답일 수 있다.
- 시간이 모자라면: 줄이는 순서는 `AuthContext` 분리가 먼저다 (밀렸을 때 규칙). 나머지는 [Day 33](./day-33.md)이나 11/26 예비일로 넘긴다.

**수치가 없으면 고치지 않는다.** "고치지 않음"이 정답인 후보가 있어도 된다. 그 기록이 산출물이다.

**수정 중 확인 (정당화된 것만)**
- `memo`를 붙이려면 어디서 props 참조가 깨지는지 Profiler로 확인한다. 인라인 콜백이 그대로면 `memo`만으로는 효과가 없고, 콜백을 안정화해도 `children`(JSX)이 새 요소라 비교가 실패할 수 있다.
- 로그 상한은 렌더 최적화가 아니라 메모리 증가 방지다. Profiler 없이 판단할 수 있다. 상한 값은 근거와 함께 정한다. `logIdRef`의 의미를 깨 key가 겹치게 만들지 않는다.
- `AuthContext` 분리는 `App.tsx`의 Provider 구조와 `useAuth` 소비자 3곳을 모두 건드린다. 측정에서 이득이 없으면 되돌린다.
- `useCallback` 의존성 배열이 틀리면 오래된 값을 잡는 버그가 된다.

**재측정**: 어제와 **같은 시나리오 4개**로 "후" 표를 만든다. 수정한 항목마다 "어떤 수치가 이 수정을 정당화했는가"를 한 줄로 쓴다. 삭제 스와이프, 롱프레스 시트, 무한스크롤이 변경 전과 같은지 확인한다.

**README 문구 갱신 (사용자 직접 과제)**: 루트 `README.md`의 "한계" 절에 "성능 최적화(`React.memo`, `getItemLayout`)와 접근성은 다루지 않음."이라는 문장이 있다. 이제 사실과 다르다. **Claude는 이 문장을 써 주지 않는다. 직접 고친다.**
- 무엇을 다뤘고 무엇을 **여전히 안 다뤘는지** 구분해서 쓴다. `getItemLayout`을 적용하지 않았다면 그대로 남긴다.
- 측정 결과 `memo`를 적용하지 않았다면 "측정 후 불필요 판단"이라고 쓰는 것이 정확하다.
- 이 파일의 git 상태를 먼저 확인한다 (10/21 기준으로는 staged인데 미션 문서는 untracked라고 적었다). 커밋 대상인지 확인 후 진행한다. 자세한 내용은 [Day 31](./day-31.md)의 "한 번만 확인할 것".

**임시 코드 되돌릴 곳**: 대체 수단으로 `<Profiler>`를 감쌌다면 감싼 화면 파일 전부.

**기록 포인트**: 후보별 판단 표(고치지 않음 포함), "후" 표, 수정 항목마다 정당화한 수치 한 줄, README 문구를 어떻게 고쳤는지.
